# Domain and design decisions

1. **Independent specification, multiple servers.** The ts-rest/Zod contract imports neither Archon nor an HTTP framework. `examples/server-express` is one sample server; another framework can implement the same `@agent-as-a-service/contract` in its own package. Within Express, `createApp({ token, implementation })` and `registerContract(app, implementation)` take a typed `ApiImplementation`. The default `notImplementedRoutes` is only a fallback. A test supplies an alternate implementation for projects while other routes still return `501`.
2. **Independent resources.** Projects are optional grouping context; conversations are chat histories; workflows are reusable versioned specifications; runs are executions. An explicit target identifies an agent or workflow, but a server with a default may omit `target` and `agentId` from responses. A conversation continues by ID without another agent ID. `localPath` is an optional server-side working directory; a backend using it must check that the path exists and that the caller can access it. If both `localPath` and `repositoryUrl` are given, the former is the working location and the latter describes its remote repository.
3. **Minimal request values.** Project and conversation creation may use `{}`. Chat requires nonempty `content`, as a string or structured parts. Run start may use `{}` when the backend has an input-free default; otherwise it can return `409` to explain what is missing. A workflow create or replace requires `specification` as a nonempty string or opaque JSON object; the backend supplies a name, engine and specification version if omitted. Path IDs, rename titles and human decisions remain required because the operation would otherwise have no subject or value. IDs are opaque nonempty strings, not necessarily UUIDs.
4. **Execution detail and streams.** Starting a run or sending chat returns `202` with a run ID. Before returning `202`, the backend must make that run available through `getRun` so a follow-up GET succeeds immediately; this is a visibility rule, not an execution deadline. Run responses require an ID, status and timestamps. Target, input, project/conversation links, output/error, executions and interactions may be absent when unavailable or inapplicable. An output-free workflow may complete successfully. Ordered run events can be polled or followed via run-scoped SSE; both share the same run event schema and sequence numbers. Conversation SSE follows chat activity across messages and can include run progress. Its `data:` field is a JSON object matching the exported `conversationEvent` schema (`id`, `conversationId`, `sequence`, `type`, optional `runId`/`data`, `createdAt`). Each stream has its own strictly increasing sequence. The SSE `id:` is its decimal sequence; `event:` is `type`. Without `Last-Event-ID`, a stream follows new events. With `Last-Event-ID`, it delivers all retained later events in order before live events. If events needed for complete replay were discarded, the backend returns `409` with `error.code: "event_history_unavailable"` before opening the stream; the same applies to `listEvents` with `after`. Retention length is deployment-specific. A server must authorize access before streaming. No workflow node vocabulary or provider session shape is required.

   The portable conversation events are `message.delta` (`data: {messageId,text}` for incremental text), `message.created` (`data: {message}` for the persisted complete message) and `run.updated` (`data: {run}`). The portable run event `run.updated` carries `data: {status}`. These payloads have exported Zod schemas and OpenAPI component references; other types are backend extensions, so clients can ignore unfamiliar types. JSON requests containing inline files can return `413 payload_too_large`; upload limits are backend-specific and no file content is echoed in that error.
5. **Human interactions.** `GET /api/v1/interactions` lists pending approvals and feedback requests visible to the caller, with optional project and cursor filters. Each item includes an interaction ID and its run ID; `getRun` gives full context. `POST /api/v1/interactions/{interactionId}/decisions` accepts `{ "decision": "approve" }`, `{ "decision": "reject", "comment": "Needs changes" }`, or another offered decision. One ID addresses one interaction, even if a run has multiple gates. A decision outside the offered choices returns `400`; omitted choices mean `approve` or `reject`. Already-resolved interactions return `409`. Success stores the decision and schedules continuation when possible. An ordinary conversation message never silently approves a gate. `resumeRun` handles separately resumable runs.
6. **Authentication and optional safeguards.** Every resource route and the status route require an HTTP bearer token in OpenAPI; only health and OpenAPI discovery are public. The credential issuer and token format remain deployment choices, so the contract adds no login or role-management routes. The example adapter checks a single development token, without identity or ownership authorization. Production backends must enforce ownership, project scope and reviewer authorization according to their deployments. `Idempotency-Key` is optional on message, run and decision writes. When present, the combination of authenticated principal, HTTP method, resolved path and key identifies one request for at least 24 hours after acceptance. Retrying an identical body returns the original status and body without duplicate side effects, including when retries overlap; changing the body returns `409 idempotency_conflict`. The example backend returns `501` before accepting these writes. A workflow GET/create/update returns a strong ETag `"v{version}"`; optional `If-Match` on update must equal the current tag or fail with `412 precondition_failed` without changing the resource. A successful update increments the version and returns the new tag. Without `If-Match`, the update is unconditional.
7. **Diagnostics and scope.** Authenticated `GET /api/v1/status` returns a server-selected list of environment variable names with `set` booleans; it never returns values or enumerates arbitrary process variables. The example reports `HOST`, `PORT` and `API_TOKEN`. Other servers can report their relevant names. `listWorkflows` includes server-provided definitions even if the caller has created none; these set `readOnly: true` and cannot be updated or deleted (`403`). The 30 resource operations leave provider settings, secrets, OAuth, webhooks, isolation environment management, admin, CLI/MCP, command discovery, dashboard-wide streaming and logs outside the contract. The [parity map](rest-parity.md) accounts for all 65 inspected Archon HTTP routes and marks omitted operations explicitly. Container deployments can inject GitHub credentials and environment configuration without adding public credential-management routes.

8. **Optional provider boundary.** `packages/agent-runtime` contains an Archon-derived TypeScript provider shape, independent of `packages/contract`. Its `sessionId` belongs to the provider and must be stored by the server under a conversation/agent or node execution, after a successful terminal `result`. The provider's `resumed` result reports whether continuity actually occurred; a false value must not be represented to clients as a resumed conversation. The server owns authentication, project authorization, persistence, SSE sequencing, cancellation, and translating provider chunks to public run/conversation events. The optional provider options are never copied directly from untrusted HTTP input. A server with no provider can still implement the REST contract.

Read the project in this order: `README.md` → `packages/contract/src/index.ts` → `packages/contract/src/v1/schemas/` → resource routers → optional `packages/agent-runtime/src/index.ts` → `examples/server-express/src/adapters/` → `examples/client/src/`.
