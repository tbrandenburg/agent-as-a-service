# Domain and design decisions

The Node-RED agents example stores `{entry, flows}`: an explicit native Link In plus the complete native flow array. Trusted authors own node/graph semantics; CRUD checks only this structural envelope and the selected Link In, stores an opaque AaaS ID/version atomically, and performs no shared deployment. Accepted runs retain immutable snapshots across update/delete. Workers load the array unchanged and become ready through host infrastructure after `flows:started`. The native `Link In -> flow -> Link Out(return)` ABI retains integrity-verified upstream host call/return semantics while removing its CLI-only single-tab/static-wire preflight, which cannot follow cross-tab Links/subflows. Runtime lookup/timeout is authoritative. Contract run input/output are recursive JSON values (null, boolean, finite number, string, array or object); conversations retain separate ContentPart semantics. Input reaches `msg.input` independently of working payload, and only the returned JSON payload becomes output. Non-JSON runtime values explicitly fail. Host-owned invocation/finalization controls identity/status; no agent conversation is required. Native credential state is separate from complete editor flow JSON.

1. **Independent specification, multiple servers.** The ts-rest/Zod contract imports neither Archon nor an HTTP framework. `examples/server-express` is one sample server; another framework can implement the same `@agent-as-a-service/contract` in its own package. Within Express, `createApp({ token, implementation })` and `registerContract(app, implementation)` take a typed `ApiImplementation`. The default `notImplementedRoutes` is only a fallback. A test supplies an alternate implementation for projects while other routes still return `501`.
2. **Independent resources.** Projects are registered working directories; conversations are chat histories; workflows are reusable versioned specifications; runs are executions. An explicit target identifies an agent or workflow, but a server with a default may omit `target` and `agentId` from responses. A conversation continues by ID without another agent ID. `POST /projects` accepts `provisioning: {kind:"empty"}`, `{kind:"clone",repositoryUrl}` or `{kind:"existing",localPath}`. An optional safe single-segment `folderName` is independent of the display `name` for empty/clone; it must be unused in the mounted root. For compatibility `{}` means empty, top-level `repositoryUrl` alone means clone, `localPath` alone means existing, and both fields mean registration of that path with repository metadata. Mixing explicit provisioning with those fields is invalid. `PATCH /projects/:projectId` changes only `name`, never files or `localPath`; deletion unregisters without erasing files. A backend must authorize and verify the path before dispatch; historical run attribution survives project deletion.
3. **Minimal request values.** Project and conversation creation may use `{}`. Chat requires nonempty `content`, as a string or structured parts. Run start may use `{}` when the backend has an input-free default; otherwise it can return `409` to explain what is missing. A workflow create or replace requires `specification` as a nonempty string or opaque JSON object; the backend supplies a name, engine and specification version if omitted. Path IDs, rename titles and human decisions remain required because the operation would otherwise have no subject or value. IDs are opaque nonempty strings, not necessarily UUIDs.
4. **Execution detail and streams.** `POST /runs.projectId` alone selects the working directory for that run: an explicit ID resolves to its registered path; omission selects the global/default directory and `run.projectId: null`, even if the workflow or conversation has project metadata. All workflows are usable in all projects. `conversationId` is chat continuity only, never a directory selector; agent and workflow runs need no pre-created conversation. Backends may reject missing or unauthorized projects before acceptance. The Node-RED agents example gives every run a separate worker process with its OS cwd set to that path, but this is not filesystem isolation: concurrent runs can access the same files. Nodes using absolute paths, their own base directory, or workflow-created worktrees require explicit paths; `msg.cwd` does not change a process cwd. Starting a run or sending chat returns `202` with a run ID. Before returning `202`, the backend must make that run available through `getRun` so a follow-up GET succeeds immediately; this is a visibility rule, not an execution deadline. Run responses require an ID, status and timestamps. Target, input, project/conversation links, output/error, executions and interactions may be absent when unavailable or inapplicable. A run can have no agent or conversation; neither a conversation link nor a conversation collection is required to create or finish a workflow run. An output-free workflow may complete successfully. Ordered run events can be polled or followed via run-scoped SSE; both share the same run event schema and sequence numbers. Conversation SSE follows chat activity across messages and can include run progress. Its `data:` field is a JSON object matching the exported `conversationEvent` schema (`id`, `conversationId`, `sequence`, `type`, optional `runId`/`data`, `createdAt`). Each stream has its own strictly increasing sequence. The SSE `id:` is its decimal sequence; `event:` is `type`. Without `Last-Event-ID`, a stream follows new events. With `Last-Event-ID`, it delivers all retained later events in order before live events. If events needed for complete replay were discarded, the backend returns `409` with `error.code: "event_history_unavailable"` before opening the stream; the same applies to `listEvents` with `after`. Retention length is deployment-specific. A server must authorize access before streaming. No workflow node vocabulary or provider session shape is required.

   `startRun` and `getRun` may return `runDetail.conversations`, a snapshot of the complete set of publicly addressable conversations linked to the run at response time. It may be `[]`; if omitted, clients can still use the optional `run.conversationId` link, but omission does not imply there are no other conversations. Each `conversationId` appears once. When both fields are present and the scalar is non-null, the collection includes `run.conversationId`; the scalar remains an optional compatibility link, not necessarily the initiating conversation. A subsequent `getRun` may add links while execution continues. Every listed ID must resolve for the caller under `GET /api/v1/conversations/:conversationId` and its messages route; private provider sessions are not public conversations. A link may include an opaque `nodeId` when the backend knows which workflow node caused the conversation; it is unrelated to `execution.id` or `execution.key`, and is optional even for workflows. Backends that cannot track public links omit the collection.

   The portable conversation events are `message.delta` (`data: {messageId,text}` for incremental text), `message.created` (`data: {message}` for the persisted complete message) and `run.updated` (`data: {run}`). The portable run event `run.updated` carries `data: {status}`. These payloads have exported Zod schemas and OpenAPI component references; other types are backend extensions, so clients can ignore unfamiliar types. JSON requests containing inline files can return `413 payload_too_large`; upload limits are backend-specific and no file content is echoed in that error.
   `runDetail.executions` is an optional snapshot of observed invocations, independent of provider conversations and of the workflow's final `run.status`. An execution's opaque `id` identifies one invocation, and `key` may identify its workflow node. `running` means input was received; `completed`/`failed` require an observed completion callback. `unconfirmed` means input was received but completion was not observed before the worker ended: it implies neither success, failure nor cancellation. An emitted message alone does not imply completion. Backends may report an incomplete trace through backend-specific run events.

5. **Human interactions.** `GET /api/v1/interactions` lists pending approvals and feedback requests visible to the caller, with optional project and cursor filters. Each item includes an interaction ID and its run ID; `getRun` gives full context. `POST /api/v1/interactions/{interactionId}/decisions` accepts `{ "decision": "approve" }`, `{ "decision": "reject", "comment": "Needs changes" }`, or another offered decision. One ID addresses one interaction, even if a run has multiple gates. A decision outside the offered choices returns `400`; omitted choices mean `approve` or `reject`. Already-resolved interactions return `409`. Success stores the decision and schedules continuation when possible. An ordinary conversation message never silently approves a gate. `resumeRun` handles separately resumable runs.
6. **Authentication and optional safeguards.** Every resource route and the status route require an HTTP bearer token in OpenAPI; only health and OpenAPI discovery are public. The credential issuer and token format remain deployment choices, so the contract adds no login or role-management routes. The example adapter checks a single development token, without identity or ownership authorization. Production backends must enforce ownership, project scope and reviewer authorization according to their deployments. `Idempotency-Key` is optional on message, run and decision writes. When present, the combination of authenticated principal, HTTP method, resolved path and key identifies one request for at least 24 hours after acceptance. Retrying an identical body returns the original status and body without duplicate side effects, including when retries overlap; changing the body returns `409 idempotency_conflict`. The example backend returns `501` before accepting these writes. A workflow GET/create/update returns a strong ETag `"v{version}"`; optional `If-Match` on update must equal the current tag or fail with `412 precondition_failed` without changing the resource. A successful update increments the version and returns the new tag. Without `If-Match`, the update is unconditional.
7. **Diagnostics and scope.** Authenticated `GET /api/v1/status` returns a server-selected list of environment variable names with `set` booleans; it never returns values or enumerates arbitrary process variables. The example reports `HOST`, `PORT` and `API_TOKEN`. Other servers can report their relevant names. `listWorkflows` includes server-provided definitions even if the caller has created none; these set `readOnly: true` and cannot be updated or deleted (`403`). The 31 resource operations leave provider settings, secrets, OAuth, webhooks, isolation environment management, admin, CLI/MCP, command discovery, dashboard-wide streaming and logs outside the contract. The [parity map](rest-parity.md) accounts for all 65 inspected Archon HTTP routes and marks omitted operations explicitly. Container deployments can inject GitHub credentials and environment configuration without adding public credential-management routes.

8. **Optional provider boundary.** `packages/agent-runtime` contains an Archon-derived TypeScript provider shape, independent of `packages/contract`. Its `sessionId` belongs to the provider and must be stored by the server under a conversation/agent or node execution, after a successful terminal `result`. The provider's `resumed` result reports whether continuity actually occurred; a false value must not be represented to clients as a resumed conversation. The server owns authentication, project authorization, persistence, SSE sequencing, cancellation, and translating provider chunks to public run/conversation events. The optional provider options are never copied directly from untrusted HTTP input. A server with no provider can still implement the REST contract.
